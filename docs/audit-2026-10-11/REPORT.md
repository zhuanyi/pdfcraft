# PdfCraft security audit and capability check (2026-10-11)

Scope: `zhuanyi/pdfcraft` at commit `bbbe600` (fork of `storytold/pdfcraft`, workspace version 0.6.0).
Environment: Linux x86_64 container, 4 vCPU, rustc 1.97.0, no display. All repo content was treated as untrusted.
This is a report only. No product code was changed.

## 1. Summary and verdict

The static audit found **no CRITICAL or HIGH issues**:

- No secrets, hidden Unicode, committed executables or opaque blobs.
- No telemetry. The only outbound network call is a user-initiated "Check for updates" GET to `api.github.com`.
- Build scripts only read repo files or an opt-in fonts directory and write to `OUT_DIR`.
- The seven vendored crates differ from their crates.io releases only by marked "PdfCraft patch" hunks, and none of those hunks add network, process or file access.
- `cargo deny check` passes. `cargo audit` reports one advisory (RUSTSEC-2023-0071, `rsa` Marvin). The repo explicitly ignores it, and I confirmed that the ignore is justified: signing uses aws-lc-rs, and `rsa` is used only for public-key verification.
- PDF JavaScript runs in an in-process Rust engine (boa) with no file, network or timer bindings. Loop and recursion limits are set.
- Document-originated links go through a scheme allowlist and a confirmation dialog.

The main finding is **MEDIUM**: a ~1 MB crafted PDF makes `render` and `text` try to allocate 5.5 GB and then 22 GB, after which the process aborts (unbounded `q` graphics-state stack, inherited from upstream hayro). That is a denial of service, not memory corruption.

Functionally, the basics work headlessly. These all **PASS** and were verified with qpdf, pdftotext, mutool and pikepdf:

- open, inspect, text extraction and rendering
- comments and page operations
- form fill (the appearance stream is regenerated)
- merge, split and extract
- AES-256 (R6) password protection
- true redaction (text removed from every stream)

PDF→Word export is **PARTIAL**: text and font sizes are kept, but layout and graphics are not. Office→PDF does not exist, as documented.

**Verdict: SAFE TO BUILD + RUN locally**, with the usual caution for any PDF tool. Opening hostile PDFs can exhaust RAM and crash the process (finding S1). The opt-in MCP server should always be started with `--root` (finding S3).

## 4. Not checked, and why

- **The GUI (`apps/pdfcraft`)** was not built or run (no display, and to save budget). The control channel, link-confirmation dialog, attachment saving and whether S1 kills the GUI process were all checked by code reading only (UNVERIFIED at runtime).
- **PDF JavaScript and XFA at runtime.** The sandbox properties (S12) come from code reading. I did not craft a malicious-JS PDF or measure the boa loop limits in practice.
- **Digital-signature validation correctness** (S2) beyond the PKCS#1 v1.5 spot check, PKCS#12 import, timestamping, and revocation (OCSP/CRL fetching, if any; `crl.entrust.net` appears in the code but I did not trace whether validation goes online).
- **OCR** (needs `cargo xtask models` downloads), **printing**, **Windows and macOS code paths**, and the **WASM build**.
- **The repo's own test suite** (`cargo test --workspace`) and **fuzzing** (`cargo xtask fuzz`) were not run, for budget reasons.
- **The release build.** I used the dev profile (which this repo configures with optimisation). Only `pdfcraft-cli` and its dependencies were built (`cargo build -p pdfcraft-cli`, 11 m 58 s).
- **A line-by-line review of the ~3.8k vendored patch lines.** They were scanned for dangerous APIs, not reviewed semantically.
- **Font and image decoders** (skrifa, zune-jpeg, hayro-jpeg2000, hayro-jbig2, tiff, png) were not fuzzed. They are memory-safe Rust and the advisory DB is clean.
- **A typosquat check** beyond name review and the parent-dependency trace.
